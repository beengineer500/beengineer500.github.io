1.1 모델은 목적이 아니라 수단 - 간극을 묻는 5가지 질문

설명용 예시값 나오는 곳
주행거리 20만 km, 정확도 1~2%p 1.2
석 달 (모델 교체 주기, 재구축 기간, 코드 무변경 기간) 2.1, 3.1, 3.2

차량 5대 오차 2·10만 원, 홀드아웃 MAE 120·118·180·135 2.6
메일 100통 (TP 6, FP 2, FN 4, TN 88) 2.6

첫 모델 2주, F1 0.03, p99 80ms, 하루 2회 배포 3.1
주행거리 60,000 km 4.2

저자는 모델 구조를 새로 설계하는 회사가 소수라고 봅니다. 대부분은 사전학습 모델을 가져와 자기 데이터로 맞춥니다.

어려운 곳은 비즈니스 요구와 인프라 사이의 간극입니다. 저자는 이 간극을 다섯 질문으로 바꿉니다.

질문 답하는 곳 (2장)
모델을 어떻게 학습시키는가 2.1.3 모델링과 학습
데이터는 어떤 경로로 모델에 전달되는가 2.1.1 데이터 수집, 2.1.2 EDA
다른 서비스와 어떻게 상호작용하는가 2.1.5 배포
어디에서 실행되는가 2.1.5 배포
시간이 지나도 정확도를 어떻게 유지하는가 2.1.6 모니터링, 2.1.7 유지보수

2장의 하위 절은 이 질문에 하나씩 답합니다. 중고차 모델에 대입하면 질문이 이렇게 바뀝니다.

  • 매물 데이터를 배치로 받는가, 실시간으로 받는가
  • 추천 가격 API를 매물 등록 화면에 동기로 붙이는가, 큐로 붙이는가
  • 모델 서버는 어느 클러스터에 두는가
  • 전기차가 늘면 누가 언제 다시 학습시키는가

1.2 ML을 쓰기 전의 질문 - 휴리스틱으로 풀 수 있는가

1장 실험 단계의 첫 질문은 "ML을 써야 하는가"입니다.

  • 규칙으로 충분하면 ML은 운영 부담만 늘린다
    • 규칙의 동작은 데이터에 따라 바뀌지 않습니다.
    • ML을 넣으면 데이터 버전, 재학습, 드리프트 감시가 따라옵니다.
  • ML은 고차원·비선형 패턴에서 값을 한다
    • 중고차 가격에는 차종, 연식, 주행거리, 사고 이력, 지역이 얽힙니다. 그래서 ML 후보입니다.
    • "주행거리 20만 km 초과 매물에 경고 표시"는 규칙 한 줄로 충분합니다.
flowchart TD
    A["풀려는 문제"] --> B{"규칙으로<br/>대부분 풀리는가"}
    B -->|"예"| C["규칙으로 시작<br/>나중에 ML로 교체 가능"]
    B -->|"아니오"| D{"패턴이 고차원·비선형이고<br/>학습 데이터가 있는가"}
    D -->|"예"| E["ML 후보 확정<br/>목표와 지표를 함께 정의"]

휴리스틱은 데이터로 학습하지 않고 사람이 정한 규칙으로 문제를 푸는 방식입니다. 코드로는 대개 if/else, 임계값, 점수 공식, 조회 테이블입니다.

기준 휴리스틱 ML
규칙의 출처 사람이 설계 데이터에서 학습
필요한 것 도메인 지식 라벨 데이터, 학습·배포·모니터링 인프라
설명 가능성 높음. 규칙을 그대로 읽으면 된다 모델에 따라 낮음
유지보수 규칙을 직접 수정 재학습, 드리프트 감시
잘 맞는 경우 규칙이 단순하고 안정적 규칙이 복잡하고 패턴이 데이터에 있음

출시 첫날부터 동작하는 휴리스틱의 예는 이렇습니다.

문제 휴리스틱
스팸 필터 제목·본문에 "무료 당첨", "대출 승인"이 있거나 링크가 5개를 넘으면 스팸
카드 이상 거래 amount > 5 * user_avg_amount 이고 결제 국가가 거주 국가와 다르면 검토
수요 예측 내일 판매량 = 지난주 같은 요일 판매량
추천 최근 7일 판매 상위 10개. 콜드 스타트에서는 인기순 추천이 정답일 때가 많다
이탈 알림 30일간 로그인이 없으면 이탈 위험
  • 휴리스틱을 ML의 기준선(baseline)으로 쓴다
    • 먼저 휴리스틱을 만들어 비즈니스 지표를 잽니다. ML 모델은 이 숫자를 넘어야 합니다.
    • 정확도가 1~2%p 오르는 정도로는 학습 파이프라인, 피처 스토어, 서빙, 모니터링의 운영 비용을 정당화하기 어렵습니다.
  • ML이 필요한 조건은 세 가지다
    • 규칙이 너무 많거나 복잡해서 사람이 다 쓸 수 없습니다. 이미지 인식과 자연어가 여기에 속합니다.
    • 규칙이 시간에 따라 자주 바뀝니다.
    • 라벨 데이터가 충분합니다.

ML을 쓸지는 비즈니스 담당자와 기술 담당자가 함께 정합니다. 2.2절이 그 판단을 질문 목록으로 구체화합니다.

1.3 ML 엔지니어의 역량 - 소프트웨어 공학·DevOps·데이터 과학

1장 1.2절은 MLOps를 세 분야의 교집합으로 그립니다(Figure 1.3).

flowchart LR
    SE["소프트웨어 공학"] --> M["MLOps<br/>세 원의 교집합"]
    DO["DevOps"] --> M
    DS["데이터 과학"] --> M

본문은 그림에 없는 데이터 엔지니어링을 하나 더 요구합니다.

분야 저자가 요구하는 수준
소프트웨어 공학 단순하지 않은 시스템을 배포해 본 경험. 디버깅과 성능 병목 분석
데이터 과학 알고리즘 전문가나 역전파의 세부까지는 불필요. TensorFlow·PyTorch·scikit-learn을 능숙하게 쓰고, 새 프레임워크를 빨리 익힘
데이터 엔지니어링 양질의 학습 데이터를 충분히 확보하는 일. 대부분의 실무자가 가장 어렵다고 꼽는 과제
DevOps 자동화와 실험 재현성. 개발·스테이징·운영에서 모델이 똑같이 동작해야 한다
  • 규제 산업에서는 재현성이 감사 요건이 된다
    • 모델이 규제 준수나 감사 대상이 되면, 같은 조건에서 같은 모델을 다시 만들 수 있어야 합니다.
  • 모든 기술을 미리 갖출 필요는 없다
    • 책은 3장에서 Kubernetes 기본기부터 시작해 플랫폼을 한 블록씩 쌓습니다.

2부. ML 생애주기 - 문제 정의부터 유지보수까지

2.1 실험 단계와 개발·스테이징·운영 단계

1장의 첫 주장은 ML 프로젝트가 배포 후에도 반복된다는 것입니다.

flowchart TD
    subgraph SW["일반 소프트웨어"]
        direction LR
        S1["코드 v1"] -->|"빌드"| P1["프로그램 A"]

데이터는 코드 변경 없이도 바뀝니다. 그래서 Git만으로는 모델을 재현할 수 없습니다. 목표는 반복 한 번의 비용을 줄이는 것입니다.

1장은 생애주기를 두 단계로 나눕니다.

관심사 실험 단계 운영 단계
목표 가능성 탐색 안정적 유지, 지속적 개선
파이프라인 자동화 거의 자동, 사람이 실행 완전 자동, 트리거가 실행
보안·윤리 느슨함 최우선 요구사항
확장성·실시간 성능 거의 무관 서비스 품질을 좌우
실패 비용 실험 한 번 사용자와 매출

트리거는 파이프라인 실행을 시작하는 신호입니다.

실험 단계는 여섯 단계입니다.

  1. 문제 정의
  2. 데이터 수집과 준비
  3. 데이터 버전 관리
  4. 학습
  5. 평가
  6. 검증

실제로는 거의 모든 단계에서 앞 단계로 되돌아갑니다. 그래서 저자는 실험 단계부터 파이프라인을 쓰라고 권합니다. 노트북 셀을 손으로 실행하면 무엇을 바꿨는지 놓치기 때문입니다.

운영 단계는 같은 절차를 완전히 자동화합니다. 그리고 끝에 배포, 모니터링, 재학습을 붙입니다. 재학습이 파이프라인을 다시 실행하면 루프가 닫힙니다. 트리거는 CI에서 오거나 다른 프로그램의 호출에서 옵니다.

  • 운영 단계에는 환경이 세 개다
    • 1장의 절 제목은 "개발·스테이징·운영 단계"입니다. 파이프라인은 모델을 이 순서로 승격(promote)합니다.
    • 운영에는 스테이징에서 검증한 모델과 이미지를 그대로 배포합니다.

1장의 두 단계를 2장의 8단계 루프(Figure 2.2)에 겹치면 이렇습니다.

2.2 문제 정의 - 세 이해관계자의 질문

"고객 이탈률을 예측하라"는 문제 정의가 아닙니다. 아래 항목이 하나도 정해지지 않았습니다.

  • 이탈의 정의 (30일 미접속인가, 해지인가)
  • 예측 시점 (얼마나 미리 알아야 하는가)
  • 대상 (전체 고객인가, 유료 고객인가)
  • 결과의 쓰임 (쿠폰 발송인가, 상담 연결인가)
  • 틀렸을 때의 비용

이 항목이 없으면 평가 지표를 고를 수 없습니다. 저자는 비즈니스, 기술, 법무 세 그룹이 모델링 전에 함께 답하라고 합니다. 원문의 질문을 성격별로 묶으면 이렇습니다.

성격 질문의 방향 이어지는 단계
필요성 정말 ML이 필요한가 1.2절
성공의 정의 성공 지표, 허용 오차, 오예측의 영향 2.6 평가
데이터 저장 위치, 파이프라인, 민감정보 2.3 수집, 2.4 EDA
자원과 운영 학습·서빙 자원, 배포 전략, 재학습 지표 2.7 ~ 2.9
위험과 규제 윤리, 개인정보, 거버넌스 3.1
  • 모델을 만들기 전에 교체 조건을 정한다
    • 기술 그룹의 질문에 "재학습을 트리거할 지표"가 있습니다.
  • 타이밍도 요구사항이다
    • 경쟁사가 비슷한 기능을 먼저 내면 같은 모델의 가치가 작아집니다.
  • 법무 질문을 빠뜨리면 다시 학습해야 한다
    • 이탈 모델을 다 만든 뒤에 상담 녹취에 별도 동의가 필요하다는 사실이 드러나면, 그 피처를 빼고 다시 학습해야 합니다.

2.3 데이터 수집 - 편향·누수와 계보

데이터 수집 단계의 편향은 이후 모든 단계로 전파됩니다. 데이터셋 요구사항은 관련성, 크기, 품질, 편향·누수 방지, 대표성, 다양성, 계보입니다. 저자는 이 중 계보를 가장 길게 다룹니다.

(용어) 계보 (lineage)

어떤 산출물이 어떤 입력으로 만들어졌는지 추적할 수 있게 남긴 기록입니다.

  • 데이터 계보 - 원본에서 학습 데이터셋까지 단계마다 버전과 메타데이터를 남긴 사슬
  • 모델 계보 - 모델 하나를 만든 코드 커밋, 설정, 데이터 버전의 연결
flowchart TD
    A["raw v1 - 원본"] -->|"ETL"| B["clean v1 - 정제본"]
    B -->|"ETL"| C["aug v1 - 증강본"]
    C -->|"ETL"| D["labeled v1 - 라벨링본"]
    D -->|"ETL"| E["dataset v1 - 학습 데이터셋"]
    D -.->|"라벨 오류 발견"| F["labeled v2부터 다시 실행"]
    F -.-> G["dataset v2"]

화살표마다 버전 관리되는 ETL 단계와 메타데이터(언제·어디서·어떻게·왜)가 붙습니다. 계보가 있으면 오류가 난 단계부터 다시 실행하면 됩니다.

저자는 계보를 미루는 것을 기술 부채로 봅니다. 임시 스크립트는 처음에만 빠릅니다. 데이터에서 오류가 나오면, 계보가 있는 팀은 쿼리 하나로 원인을 찾고 계보가 없는 팀은 추출 스크립트를 처음부터 다시 짭니다.

  • 첫 데이터셋은 거의 최선이 아니다
    • 그래서 저자는 고칠 수 있는 데이터셋을 만들라고 합니다.
  • 메타데이터는 언제, 어디서, 어떻게, 왜를 남긴다
    • 가장 자주 빠지는 항목은 "왜"입니다.
    • 사기 탐지용으로 의심 거래만 모은 데이터가 있다고 해봅시다. 이 데이터를 일반 거래 분석에 쓰면 결과가 왜곡됩니다.

원문은 중고차 가격 모델의 수집 지침을 이렇게 정합니다. 중고 시장의 승용차 데이터는 모두 모으고, 트럭과 오토바이는 뺍니다. 표본이 목표 도메인을 대표하도록 샘플링하고, 버전 관리되는 ETL 파이프라인으로 데이터셋을 만듭니다.

한 플랫폼에서만 수집한 데이터는 그 플랫폼의 고객층에 치우칠 수 있습니다. 지방 저가 차량이 부족하면 그 매물을 보강한 v2를 만듭니다. 버전 관리되는 ETL이 있으면 v1과 v2로 학습한 모델을 비교할 수 있습니다.

수집과 큐레이션

수집은 데이터를 어디서 얼마나 가져올지 정하는 일입니다. 큐레이션은 가져온 원시 데이터를 모델링에 쓸 수 있게 고르고 다듬는 일입니다.

큐레이션 작업 내용 예시
선별 목적에 맞는 데이터만 고름 흐릿하거나 잘린 신분증 이미지 제외
정제 오류·중복·결측 수정 또는 제거 같은 거래의 중복 행, 음수 금액 제거
균형 조정 특정 부류 쏠림 완화 사기가 0.1%면 사기 샘플 보강
대표성 확보 실제 운영 환경을 반영 여러 국가·기기·조명의 신분증 포함
문서화 출처와 기준을 기록 데이터 카드, 데이터셋 버전 태그

균형 조정은 학습 데이터에만 합니다. 검증·테스트 데이터까지 조정하면 분포가 운영 환경과 달라지고, 점수가 실제보다 높게 나옵니다.

원문은 이 단계에서 연구와 기업이 갈린다고 봅니다. 연구자는 여러 차례 검토와 수정을 거친 대규모 오픈소스 데이터셋을 쓰고 품질이 충분하다고 가정합니다. 기업은 자기 도메인에 맞는 오픈 데이터셋이 없는 경우가 많습니다. 있더라도 배포 환경의 데이터로 미세 조정(전이 학습)을 해야 합니다.

편향과 누수

편향은 데이터가 현실과 다른 문제이고, 누수는 평가가 현실과 다른 문제입니다. 둘 다 학습 뒤에는 고치기 어렵습니다. 그래서 원문은 수집·큐레이션 단계에서 막으라고 합니다.

편향 원인 예시
표본 편향 데이터가 세상을 골고루 담지 못함 밝은 실내의 신분증만 학습하면 어두운 곳에서 휴대폰으로 찍은 사진을 못 찾음
선택 편향 라벨이 붙은 데이터가 특정 경우에 쏠림 고객이 신고한 거래만 사기로 표시하면 신고되지 않은 사기를 놓침
과거 편향 과거의 불공정한 판단을 그대로 학습 과거 대출 심사의 차별을 모델이 재현
누수 원인 예시
샘플 중복 같은 데이터가 학습과 테스트에 모두 들어감 같은 신분증 사진이 두 번 수집됨
미래 정보 예측 시점에 알 수 없는 값을 피처로 씀 3월 1일 거래의 사기 판정에 3월 5일에 계산한 "최근 7일 평균 결제액"을 씀
정답 단서 정답을 간접적으로 알려 주는 피처 사기 확정 뒤에 생기는 "계정 정지 여부"를 피처로 씀

누수를 막는 규칙은 네 가지입니다.

  1. 분할 전에 중복을 제거합니다.
  2. 시간 순서가 있는 데이터는 무작위로 섞지 않고 시간 순서로 나눕니다.
  3. 피처마다 "예측 시점에 이 값을 알 수 있는가"를 묻습니다.
  4. 점수가 지나치게 좋으면 누수를 먼저 의심합니다.

라벨과 데이터셋 분할

라벨이 붙은 데이터는 입력 X와 정답 y의 쌍입니다. 라벨을 얻는 길은 세 가지입니다.

방법 누가 정답을 붙이나 책의 예
애노테이션 사람이 직접 CVAT로 신분증 둘레에 경계 상자를 그리고 ID 번호를 입력
사건 업무 중 생긴 기록 고객이 "내가 한 결제가 아니다"라고 신고한 거래
합성 데이터 프로그램이 생성할 때 함께 신분증 템플릿을 배경에 붙이면 네 모서리 좌표가 정답이 됨

합성 데이터는 사람의 라벨 오류가 없고 대량으로 만들 수 있습니다. 대신 실제와 너무 다르면 운영에서 성능이 떨어집니다. 그래서 합성 데이터로 학습하더라도 평가는 실제 데이터로 합니다.

사람 애노테이션은 한 번으로 끝나지 않습니다. 사람과 모델이 번갈아 일하는 루프가 됩니다(human-in-the-loop).

1. 사람   CVAT에서 초기 라벨링
2. 모델   그 라벨로 학습
3. 모델   새 이미지의 경계 상자를 제안
4. 사람   틀린 상자를 고치고 맞는 상자를 승인
5. 모델   고친 라벨을 더해 재학습 → 3번으로

라벨이 붙은 데이터는 학습·검증·테스트로 나눕니다.

구분 학습 (train) 검증 (validation) 테스트 (test)
용도 모델이 패턴을 학습 하이퍼파라미터 조정, 모델 선택 최종 성능 1회 측정
학습에 쓰나 예 간접적으로 영향 절대 아니오
통상 비율 60~80% 10~20% 10~20%

배포 뒤의 실시간 요청에는 정답이 없습니다. 사기 라벨은 신고까지 며칠이 걸립니다. 그래서 2.8절의 성능 모니터링은 라벨이 도착한 뒤에야 할 수 있습니다.

영화 추천 프로젝트는 데이터셋을 다른 기준으로 한 번 더 나눕니다. 운영 중에 데이터가 계속 쌓이는 상황을 흉내 내려고 도착 시점별 조각으로 자릅니다.

버전 포함된 데이터 흉내 내는 상황
v1 첫 조각 서비스 시작 때 확보한 데이터
v2 v1 + 두 번째 조각 한 달 뒤 사용자 데이터 추가
v3 v2 + 세 번째 조각 두 달 뒤 또 추가

각 버전 안에서도 학습·검증·테스트 분할은 그대로 필요합니다.

2.4 EDA - 가정을 리스크로 다룬다

EDA(탐색적 데이터 분석)는 잘못 정의된 문제와 숨은 가정을 찾습니다. 검증 전의 가정은 리스크로 다룹니다.

원문의 EDA 질문은 대부분 운영에서 생길 문제를 묻습니다.

EDA 질문 운영에서의 의미
스키마가 바뀔 수 있는가 상위 시스템이 컬럼을 바꾸면 모델이 망가진다. 입력 검증이 필요하다
피처 계산 비용이 비싼가 실시간 서빙에서 지연 시간이 커진다
입력이 주기적으로 변하는가 계절성과 이벤트가 미래의 드리프트 후보다
운영 중 이상치는 어떻게 처리하는가 운영에서는 이상치 요청에도 응답해야 한다
  • 가정을 목록으로 만들어 자동 검사로 넣는다
    • amount 필드를 원화로 가정했는데 일부가 달러일 수 있습니다.
    • created_at을 UTC로 가정했는데 한국 시간일 수 있습니다.
    • 이런 문제는 모델 코드에서 보이지 않습니다. 파이프라인 초반의 검사가 잡습니다.
  • EDA로 공수를 추정한다
    • 데이터가 지저분할수록 정제와 운영 검증에 시간이 더 듭니다.
  • ML 엔지니어도 EDA를 알아야 한다
    • EDA에서 본 분포를 아는 엔지니어가 드리프트를 먼저 의심합니다.

변수 하나씩 보아서는 피처의 단서가 잘 드러나지 않습니다. 키와 몸무게를 따로 보면 둘 다 평범해도, 키에 비해 몸무게가 큰 사람이 있습니다. 이 관계가 BMI 같은 새 피처가 됩니다. 원문은 이런 다변량 분석(multivariate analysis)을 권합니다.

변수가 수십수백 개면 눈으로 볼 수 없습니다. 이때 차원 축소로 23차원에 그립니다.

기법 방식 강점 주의
PCA 가장 넓게 퍼진 방향으로 선형 투영 빠르고 결과가 일정함. 피처 축소에도 씀 비선형 구조는 못 잡음
t-SNE 가까운 점끼리 가깝게 비선형 배치 군집 구조 시각화 느리고 실행마다 결과가 다름. 군집 간 거리는 해석하지 않음

EDA는 한 번으로 끝나지 않습니다. 실험이 실패할 때마다 가정을 다시 검토합니다.

2.5 모델링과 학습 - 모델 = 코드 + 설정 + 데이터

이 책의 모델링 절은 학습 기법 대신 학습 과정 추적을 다룹니다.

모델링은 모델 유형을 고르는 데서 시작합니다. 유형은 모델이 무엇을 출력하는가로 나뉩니다.

유형 질문 출력 예시
분류 이것은 무엇인가 정해진 범주 하나 스팸 여부
탐지 무엇이 어디에 있는가 범주와 위치(경계 상자) 사진 속 신분증 위치
회귀 얼마인가 연속적인 숫자 중고차 가격

같은 소재도 출력에 따라 유형이 바뀝니다. 영화 평점을 "좋음"과 "나쁨" 중 하나로 맞히면 분류이고, "3.7점"으로 맞히면 회귀입니다.

저자가 꼽는 MLOps 도구는 네 가지입니다.

  • 모델·데이터 버전 관리
  • 실험 추적(experiment tracking)
  • 학습 파이프라인
  • 하이퍼파라미터 탐색

네 도구의 공통 원칙은 계보, 추적, 수작업 제거입니다.

탐색 도구는 설정만 바꿔서 학습을 반복합니다. 그래서 하이퍼파라미터를 코드에서 분리합니다.

하드코딩                              설정 분리

model = Net(layers=6)                 # config.yaml
opt = Adam(lr=0.001)                  layers: 6
# 값이 코드 여기저기에                lr: 0.001

                                      model = build(cfg)

탐색 도구가 값을 못 바꿈              탐색 도구가 config만 바꿔 반복 실행
→ 사람이 매번 코드 수정               → 자동화 + 실행마다 기록

계보와 재현성을 위해 실행마다 설정을 기록합니다. 저자는 학습된 모델을 코드에 설정과 데이터를 적용한 산출물로 정의합니다.

Figure 2.5는 이 정의를 재학습 파이프라인 두 단계로 나눕니다. 설정도 모델 설정과 학습 설정 두 개입니다.

flowchart TD
    subgraph SETUP["셋업"]
        W["사전학습 가중치"] --> P1(("+"))
        C["코드<br/>Git a1b2"] --> P1
        MC["모델 설정<br/>model-config v7"] --> P1
    end
    P1 --> M["모델<br/>구조 + 초기 가중치"]
    subgraph TRAIN["학습"]
        M --> P2(("+"))
        D["데이터셋<br/>dataset v3"] --> P2
        TC["학습 설정<br/>train-config v4"] --> P2
    end
    P2 --> T["학습된 모델<br/>model v12"]
    T -.->|"다음 재학습의<br/>출발점"| W

다섯 입력은 각자 버전을 가집니다. 역방향으로는 model v12를 만든 사전학습 가중치, 코드 a1b2, 모델 설정 v7, 학습 설정 v4, 데이터 v3를 찾습니다. 순방향으로는 dataset v3로 학습한 모델을 찾습니다.

  • 설정 파일만 고쳐 가설을 검증한다
    • 과적합이 의심되면 "모델이 너무 크다"는 가설을 세웁니다.
    • 코드를 열지 않고 num_layers나 hidden_size만 줄여 재학습합니다. 검증 성능이 오르면 가설이 맞습니다.
    • 설정 파일을 Git으로 추적하면, 성능이 떨어진 두 모델의 설정을 diff로 비교할 수 있습니다.
  • 모델 파일과 코드는 버전이 따로 바뀐다
    • 코드는 그대로 두고 새 데이터로 모델만 바꾸기도 합니다. 반대로 모델 파일은 그대로 두고 전처리 코드만 고치기도 합니다.
    • 그래서 코드는 Git에, 모델 파일은 레지스트리나 객체 스토리지에 둡니다. 모델에는 짝이 되는 코드 커밋을 메타데이터로 남깁니다.

모델 파일에 무엇이 들어 있는지는 저장 방식이 정합니다.

저장 방식 담기는 것 로드할 때 필요한 것
가중치만 (PyTorch state_dict) 숫자(가중치)만 모델 구조를 정의한 코드
가중치 + 연산 구조 (TorchScript, ONNX, SavedModel) 숫자와 연산 그래프 원래 코드 없이 로드·실행 가능
pickle 전체 객체 클래스 경로를 포함한 객체 전체 원래 클래스 코드와 같은 경로·버전

state_dict로 저장한 가중치는 구조를 바꾼 코드에 넣으면 크기가 맞지 않아 오류가 납니다. 더 나쁜 경우에는 오류 없이 엉뚱한 결과가 나옵니다. pickle 파일은 로드할 때 코드를 실행할 수 있습니다. 그래서 출처를 모르는 모델 파일을 pickle.load하면 보안 위험이 있습니다.

  • 실험 추적은 잘못된 결론을 막는다
    • 팀원 A가 레이어를 6에서 4로 줄였더니 검증 손실이 좋아졌다고 보고합니다.
    • 팀원 B가 추적 서버에서 두 실행을 비교합니다. 데이터셋 버전이 다릅니다.
    • 원인을 가릴 수 없으므로 팀은 다시 실험합니다.
  • 설정 항목을 너무 늘리지 않는다
    • 저자는 팩토리 패턴으로 설정에서 모델 객체를 만들라고 권합니다. 동시에 과도한 파라미터화(overparametrization)를 경계합니다.
    • 모든 값을 설정으로 빼면 설정 파일이 코드만큼 복잡해집니다. 자주 바꾸는 값부터 뺍니다.

2.6 평가와 검증 - 지표 선택과 홀드아웃 버전

1장은 평가(evaluation)와 검증(validation)을 구분합니다.

구분 평가 검증
누가 모델을 만든 팀 비즈니스 이해관계자
무엇으로 학습에 쓰지 않은 데이터와 정량 지표 업무 기준과 사례 검토
묻는 것 보지 못한 데이터에서 숫자가 괜찮은가 이 모델을 내보내도 되는가
중고차 예시 테스트 세트 평균 오차가 기준 이하인가 희귀 차종에 터무니없는 가격이 나오지 않는가

평가를 통과해도 검증에서 떨어질 수 있습니다. 지표가 업무 요구를 다 담지 못하기 때문입니다.

2장은 평가를 문제 정의와 연결합니다. 지표를 고르려면 어떤 오류가 누구에게 어떤 피해를 주는가를 먼저 정해야 합니다.

                 예측: 양성     예측: 음성
실제: 양성         TP             FN (놓침)
실제: 음성         FP (헛경보)    TN

Precision = TP / (TP + FP)   양성이라고 한 것 중 진짜 비율 → 헛경보가 아플 때
Recall    = TP / (TP + FN)   진짜 양성 중 잡아낸 비율     → 놓침이 아플 때

원문은 의료가 precision을, 금융이 recall을 중시할 수 있다고 예를 듭니다. 같은 의료라도 암 선별 검사는 recall이 우선입니다. 놓침이 치명적이기 때문입니다.

메일 100통 중 진짜 스팸이 10통이라고 해봅시다. 모델이 8통을 스팸으로 판정했고, 그중 6통이 진짜입니다. 그러면 TP 6, FP 2, FN 4, TN 88입니다.

지표 식 값
Precision TP / (TP + FP) 6 ÷ 8 = 0.75
Recall TP / (TP + FN) 6 ÷ 10 = 0.60
F1 2 × P × R / (P + R) 0.90 ÷ 1.35 = 0.667
Accuracy (TP + TN) / 전체 94 ÷ 100 = 0.94
  • 불균형 데이터에서는 Accuracy가 높게 나온다
    • 모든 메일을 정상이라고 찍어도 Accuracy는 0.90입니다.
  • F1은 조화평균이라 한쪽이 낮으면 크게 떨어진다
    • 모든 메일을 스팸이라고 찍으면 Recall 1.0, Precision 0.1입니다. 산술평균은 0.55이고 F1은 0.18입니다.

차량 5대의 오차(만 원)로 평균 절대 오차(MAE)와 평균 제곱 오차(MSE)를 비교합니다.

모델 5대 오차 MAE MSE
A 2, 2, 2, 2, 2 10 ÷ 5 = 2.0 20 ÷ 5 = 4.0
B 0, 0, 0, 0, 10 10 ÷ 5 = 2.0 100 ÷ 5 = 20.0

MSE는 큰 오차를 더 크게 반영합니다.

  • 홀드아웃셋도 버전 관리한다
    • 홀드아웃셋은 학습에 쓰지 않고 최종 평가에만 쓰는 데이터입니다.
    • 운영 분포가 바뀌면 홀드아웃셋도 갱신합니다.
    • 그래서 점수마다 홀드아웃 버전을 함께 기록합니다.
점수(MAE) 홀드아웃 v1 홀드아웃 v2 (전기차 추가)
모델 v3 120 180
모델 v4 118 135

같은 홀드아웃 버전끼리만 비교합니다.

분할 규칙도 고정합니다. 학습·테스트·홀드아웃 분할이 바뀌면 예전 평가 데이터 일부가 새 학습 데이터로 들어갑니다. 그러면 이전 평가 점수를 믿을 수 없고, 재평가와 재학습이 필요합니다. 그래서 분할의 시드와 기준을 버전으로 남깁니다.

원문은 점수 계산 뒤에 할 일을 세 가지 더 듭니다.

  • 오분류 샘플을 분석해 데이터 수집으로 돌려보낸다
    • 틀린 샘플의 패턴에서 모델의 체계적 문제와 편향을 찾습니다.
  • 민감도와 견고성을 검사한다
    • 적대적 테스트와 엣지 케이스 시뮬레이션으로 운영에서 생길 오류를 미리 찾습니다.
  • 해석 가능성을 요구하는 조직도 있다
    • 피처 중요도와 결정 경계를 보거나, LIME·SHAP 같은 설명 기법을 씁니다.
    • 저자는 구현이 복잡하므로 요구사항과 비교해 도입을 정하라고 합니다.

2.7 배포 - 평가한 모델을 그대로 배포한다

모델은 배포되어야 가치를 만듭니다. 저자는 배포 방식을 둘로 나눕니다.

  • API 엔드포인트 뒤에 두는 마이크로서비스
  • 하드웨어나 엣지 디바이스에 직접 올리는 방식

두 방식 모두 지연 시간이 중요합니다. 그래서 배포 전에 최적화 단계가 들어갑니다.

FP32 가중치를 INT8로 양자화하면 크기가 약 1/4이 됩니다. 대신 특정 클래스의 정확도가 떨어질 수 있습니다. 그래서 저자는 최적화된 최종 모델로 다시 평가하라고 합니다.

flowchart TD
    A["학습된 모델"] --> B["최적화<br/>양자화 등"]
    B --> C["최적화 모델로 재평가"]
    C --> D["스테이징<br/>운영 모델과 비교"]
    D --> E["운영"]
    E -.->|"이상 발생"| F["레지스트리의<br/>이전 버전으로 롤백"]
  • ML의 스테이징은 평가 모드다
    • 스테이징에서 새 모델과 운영 모델을 실제 데이터로 비교합니다.
    • 새 모델이 기준을 통과하면 파이프라인이 자동으로 승격합니다.
    • 전환 기록이 있으므로 롤백은 운영 표시를 이전 버전으로 바꾸는 일입니다.
  • 배포 범위는 단계적으로 넓힌다
    • 섀도 배포는 실제 트래픽을 복제해 스테이징에 흘립니다.
    • 카나리 배포는 사용자 5%에게만 새 모델을 보여 줍니다.
    • 지표가 정상이면 50%, 100%로 넓힙니다. 이상하면 0%로 되돌립니다.

1장은 배포 점검표를 줍니다. REST API로 감싸는 것은 출발점일 뿐입니다(slapping on a REST API).

점검 항목 확인 질문 중고차 예시
부하 테스트 예상 트래픽을 견디는가 매물 등록이 몰리는 주말 저녁
오토스케일링 폭증에 자동으로 늘어나는가 TV 광고 직후 등록 폭증
배포 버전 관리 지금 떠 있는 것이 어느 모델, 어느 이미지인가 price-model v3, 이미지 태그 기록
롤백 전략 몇 분 안에 이전 버전으로 돌아가는가 v3 이상 시 v2로 즉시 되돌림

책은 BentoML로 모델을 HTTP 엔드포인트로 만듭니다. 그다음 Docker로 패키징하고, Yatai로 Kubernetes에 배포합니다. 그래서 3장이 Kubernetes로 시작합니다.

저자는 데이터 과학자도 배포에 참여하라고 권합니다. 모델을 만든 사람이 지연 시간과 메모리 제약을 알아야 모델을 고칠 수 있습니다.

2.8 모니터링 - 데이터·성능·오류 세 종류

저자는 운영 데이터를 만난 모델의 성능이 대개 떨어진다고 봅니다. 그래서 모니터링은 배포와 동시에 갖춥니다.

ML 모델은 200 OK와 함께 틀린 예측값을 돌려줄 수 있습니다.

층 무엇을 보는가 대표 지표 중고차 예시
시스템 서비스가 살아 있고 빠른가 RPS, HTTP 상태 코드, 지연 시간 5xx 비율 급증
ML 고유 입력과 예측이 학습 때와 비슷한가 데이터 드리프트, 개념 드리프트 전기차 비중 급증
비즈니스 모델이 가치를 만드는가 이탈률, 전환율 추천 가격 수락률

시스템 층이 정상이어도 위의 두 층은 나빠질 수 있습니다. BentoML의 기본 Prometheus 지표는 시스템 층만 봅니다.

(용어) 데이터 드리프트와 개념 드리프트

둘 다 재학습의 신호입니다. 감지 방법이 다릅니다.

  • 데이터 드리프트 - 입력의 분포가 학습 때와 달라지는 것. 예를 들어 평균 연식이 6년에서 2년이 됩니다. 입력만 봐도 감지할 수 있습니다.
  • 개념 드리프트 - 입력과 정답 사이의 관계가 바뀌는 것. 예를 들어 같은 연식인데 유가 변동으로 디젤차 시세가 떨어집니다. 정답이 도착해야 감지할 수 있습니다.

2장은 모니터링을 세 종류로 나눕니다. 표의 순서는 감지가 빠른 순서입니다.

종류 정답 라벨 감지 속도 얻는 정보
데이터 모니터링 불필요 가장 빠름 입력이 달라졌다
성능 모니터링 필요 라벨 도착 후 결과가 나빠졌다
오류 모니터링 필요 + 사람 분석 가장 느림 왜, 어디서 틀리는가

중고차 모델에서는 이렇게 이어집니다.

  1. 데이터 모니터링이 입력 매물의 평균 연식 하락을 잡습니다.
  2. 몇 주 뒤 실거래가가 쌓입니다. 성능 모니터링에서 MAE가 오릅니다.
  3. 오류 모니터링이 출고 1년 미만 차량의 과소 예측을 찾습니다.
  4. 데이터 수집 단계에서 신차급 매물을 보강합니다. 그다음 모델을 다시 학습합니다.

책은 1번의 분포 비교와 재학습 트리거에 Evidently를 씁니다.

  • 모니터링에는 계보가 필요하다
    • 경보가 울리면 언제부터, 어느 모델 버전에서 나빠졌는지 알아야 합니다. 그 답은 2.3절의 계보에 있습니다.
  • 요청 로그로 엣지 케이스를 재현한다
    • 로그가 있으면 특정 코드 변경이 만든 문제를 추적할 수 있습니다.
    • 로그와 버전 기록을 함께 남기면 규제 산업에서 문서화 수단이 됩니다.
  • 알림이 담당자에게 닿아야 한다
    • 아무도 보지 않는 대시보드는 지표가 없는 것과 같습니다. 너무 많은 알림도 결과가 같습니다.
    • 수신자, 임계값, 런북을 미리 정합니다.

2.9 유지보수와 재학습 - 루프를 닫는다

유지보수에는 버그 수정, 엣지 케이스 데이터 수집, 드리프트 대응 재학습이 있습니다.

flowchart TD
    A["주기 기반<br/>예: 매월 1일"] -->|"달력이 실행"| P["학습 파이프라인"]
    B["임계값 기반<br/>예: 추천 가격 수락률 급락"] -->|"모니터링이 실행"| P
    P --> Q["평가"] --> R["배포"]
구분 주기 기반 임계값 기반
장점 예측 가능하고 운영 계획이 쉽다 필요할 때만 빠르게 대응한다
단점 급변에 늦고, 변화가 없어도 비용이 든다 임계값 설계가 어렵고, 라벨이 늦으면 감지도 늦다

실무에서는 두 트리거를 함께 씁니다. 저자는 하나를 더 강조합니다. 재학습을 자동화하려면 배포도 자동화해야 합니다. 배포가 수작업이면 새 모델이 운영에 나가는 데 며칠이 걸립니다.

sequenceDiagram
    participant Mon as 모니터링
    participant Pipe as 학습 파이프라인
    participant Reg as 레지스트리
    participant Srv as 서빙
    Mon->>Mon: 수락률이 임계값 아래로
    Mon->>Pipe: 트리거 + 담당자 알림
    Pipe->>Pipe: 학습·평가·검증
    Pipe->>Reg: v4 등록 (스테이징)
    Reg->>Srv: v4 운영 승격
    Srv->>Mon: v4 지표 전송
    Mon->>Reg: 오류율 급증
    Reg->>Srv: v3로 롤백

2장에서 유지보수는 생애주기의 모든 단계에서 합니다.

단계 그 단계의 유지보수
데이터 수집 상위 시스템 스키마 변경 대응, 드리프트 대응 데이터 보강
EDA 새 데이터로 가정 재검증
모델링·학습 라이브러리 업그레이드, 새 구조 실험
평가 엣지 케이스 테스트 추가, 홀드아웃셋 갱신

3부. DevOps와 MLOps

3.1 MLOps가 어려운 일곱 가지 이유

원문 2.2절은 MLOps를 건너뛰면 기술 부채가 쌓인다고 결론 냅니다.

# 어려움 (원문 2.2) 넘었을 때의 이점 (원문 2.3)
1 블록마다 복잡도가 곱해진다 실험 가속. 인프라가 추상화된다
2 데이터 관리 실패는 소송으로 이어진다 재현성과 추적성
3 시스템 전체의 구조적 결함이 보이지 않는다 CI/CD로 반복 작업 자동화
4 직군마다 다른 지표로 말한다 공통 도구로 협업
5 대규모 트래픽은 다른 문제를 만든다 표준 워크플로우로 확장
6 엣지 케이스는 에러 없이 결과만 틀린다 모니터링과 롤백
7 도구 생태계가 파편화되어 있다 공유 컴포넌트로 중복 투자 제거

4번은 같은 사실을 직군마다 다른 지표로 말하는 문제입니다.

flowchart TD
    DS["데이터 과학자<br/>F1이 0.03 올랐다"] --> T["실험 추적 서버·대시보드<br/>같은 실행 기록"]
    MLE["ML 엔지니어<br/>p99 80ms, 하루 2회 배포"] --> T
    BIZ["비즈니스<br/>CS 비용 월 X원 절감"] --> T

플랫폼 엔지니어가 학습 코드에 모델 로깅을 기본 설정하면, 데이터 과학자는 별도 작업 없이 버전을 남깁니다.

7번의 예로 원문은 모델 레지스트리 솔루션만 최소 10가지라고 씁니다. 포괄적 솔루션은 데이터 관리나 계보 같은 핵심을 놓치는 경우가 많습니다. 그래서 저자는 전문 도구 몇 개와 포괄적 솔루션을 섞는 방식이 현재의 주류라고 봅니다.

세 명의 팀이 첫 모델을 수작업으로 2주 만에 냅니다. 반년 뒤에는 모델 다섯 개의 학습 데이터를 추적하지 못합니다. 모델을 다시 만드는 데 석 달이 걸립니다.

3.2 DevOps와 다른 점 - CI/CD에 CT가 붙는다

MLOps와 DevOps는 자동화, CI/CD, 협업을 공유합니다. 원문의 차이점 여섯 가지는 대부분 한 사실에서 나옵니다. ML 시스템의 동작은 코드와 데이터가 함께 정합니다.

flowchart LR
    R["ML 시스템의 동작은<br/>코드와 데이터가 함께 정한다"]
    R --> A["데이터 라이프사이클 관리<br/>데이터가 모델의 일부"]
    R --> B["지속 학습 CT<br/>코드 변경 없이 재학습"]
    R --> C["편향·해석 가능성<br/>데이터 편향이 모델로 간다"]
    R --> D["성능 저하 감시<br/>입력이 바뀌면 성능이 떨어진다"]
    R --> E["실험 추적<br/>좋은 데이터·설정을 미리 모른다"]

(용어) CT (Continuous Training, 지속 학습)

데이터 변화를 트리거로 모델을 자동으로 다시 학습시키는 체계입니다.

  • CI/CD의 트리거 - 코드 커밋
  • CT의 트리거 - 새 데이터 도착, 드리프트 감지, 성능 저하. 코드가 바뀌지 않아도 파이프라인이 실행됩니다.
flowchart TD
    subgraph DEV["DevOps에도 있는 흐름"]
        direction TB
        A["코드 커밋"] --> B["CI/CD<br/>빌드·테스트"] --> C["서비스 배포"]
    end
    subgraph MLOPS["DevOps에 없는 흐름"]
        direction TB
        D["새 데이터·드리프트<br/>성능 저하"] --> E["CT 재학습·검증<br/>코드 변경 없음"] --> F["새 모델 배포"]
    end

코드 커밋만 트리거로 쓰면, 코드가 석 달 동안 그대로일 때 재학습도 없습니다. 그사이 사용자 행동이 바뀌면 성능만 떨어집니다.

MLOps는 빌드뿐 아니라 실험도 추적합니다. 실패한 실험도 기록합니다. 그래야 팀원이 같은 실험을 반복하지 않습니다.

3.3 성숙도 Level 0 → 1 → 2

2장은 Google의 기준으로 성숙도를 나눕니다. 레벨을 가르는 질문은 무엇을 배포하는가입니다.

flowchart BT
    L0["Level 0 - 모델 파일을 배포<br/>수동 스크립트, 모니터링 없음, 드문 릴리스"]
    L1["Level 1 - 학습 파이프라인을 배포<br/>지속 학습, 컴포넌트 공유, 실험-운영 대칭"]
    L2["Level 2 - 파이프라인을 만드는 시스템을 배포<br/>파이프라인 빌드·배포 자동화, 조직 전체가 소유"]
    L0 --> L1 --> L2
루프 단계 Level 0 Level 1 Level 2
데이터 추출·검증 수동 자동 자동
데이터·모델 분석 수동 수동 수동
학습 수동 자동 자동
평가 수동 자동 자동
모델 배포 수동 자동 자동
모니터링·재학습 트리거 없음 자동 자동
파이프라인 자체의 빌드·배포 수동 수동 자동

Google의 원 도식 세 장에는 공통으로 경계선 두 개가 있습니다. 가로 점선 위는 실험·개발·테스트 환경이고, 아래는 스테이징·운영 환경입니다. 세로 점선 ML | Ops는 데이터 과학자가 운영 쪽에 무엇을 넘기는지 보여 줍니다.

  • Level 1의 핵심은 실험-운영 대칭성이다
    • 실험과 운영에서 같은 파이프라인을 씁니다(experimental-operational symmetry).
    • 노트북은 결측값을 평균으로 채우고 운영 코드는 0으로 채운다고 해봅시다. 그러면 같은 입력이 학습 때와 서빙 때 다른 피처 값이 됩니다. 이런 어긋남을 학습-서빙 불일치라고 합니다(4.2절).
    • 같은 컴포넌트를 양쪽에서 쓰면 이 불일치가 생기지 않습니다.
  • Level 1은 사람의 판단을 규칙으로 적는다
    • 필요조건은 데이터 검증, 모델 검증, 피처 스토어(필요할 때), 파이프라인 모니터링, 계보, 트리거입니다.
    • "이 데이터 괜찮나"는 데이터 검증이 됩니다. "언제 재학습하나"는 트리거가 됩니다.
  • Level 2에서도 분석은 사람이 한다
    • 데이터 분석과 모델 분석은 자동화되지 않습니다.
    • Level 2에서는 조직 전체가 파이프라인을 소유합니다. 데이터 과학자도 컴포넌트를 기여합니다.

레벨은 다음 단계를 계획하는 기준입니다. 레벨 사이의 난이도는 일정하지 않습니다. 영화 추천 프로젝트는 Level 0에서 시작합니다. 학습 파이프라인과 드리프트 트리거를 갖추면 Level 1입니다.

4.2 네 도구가 푸는 문제 - Kubeflow Pipelines·Feast·MLflow·CI/CD

1.3.3절은 도구 네 블록을 출발점으로 제시합니다.

도구 블록 생애주기 위치 없을 때의 문제 책의 선택
파이프라인 자동화 전 단계를 연결 단계 순서를 틀리고, 무엇을 돌렸는지 잊는다 Kubeflow Pipelines
피처 스토어 데이터 수집과 준비 팀마다 같은 피처를 다시 만들고, 학습과 서빙의 값이 어긋난다 Feast
모델 레지스트리 학습·평가 이후 어느 실행이 어떤 모델을 만들었는지 모른다 MLflow
배포 자동화 배포·재학습 이후 배포가 느리고 사람마다 방식이 다르다 컨테이너 + CI/CD + Kubernetes
  • 파이프라인은 단계 사이의 전달을 맡는다
    • Kubeflow Pipelines에서 각 단계는 컴포넌트입니다. 컴포넌트는 앞 출력을 받아 다음 컴포넌트로 넘깁니다.
    • 파이프라인 정의가 실행 순서와 입출력을 고정하고, Kubeflow Pipelines가 실행마다 기록을 남깁니다.
  • 피처 스토어의 이점은 두 가지다
    • 팀끼리 피처를 공유합니다.
    • 학습-서빙 불일치를 막습니다.

(용어) 학습-서빙 불일치 (training-serving skew)

학습 때 모델이 본 데이터와 추론 때 보는 데이터가 어긋나는 현상입니다. 대표 원인은 학습과 서빙의 데이터 변환 코드가 서로 다른 것입니다. 서버는 정상 응답하므로 놓치기 쉽습니다.

flowchart TD
    subgraph NO["피처 스토어 없이 - 변환 코드 두 벌"]

        A["데이터팀 SQL<br/>주행거리 km, 결측치 중앙값"] --> A2["학습"]

    subgraph YES["피처 스토어 사용 - 피처 정의 한 벌"]
        direction TB
        F["피처 정의<br/>주행거리_km, 결측 처리 규칙"] -->|"오프라인"| T["학습 데이터"]

피처 스토어는 저장소 두 개를 함께 둡니다. 피처 정의는 하나이고, 오프라인 스토어의 값을 온라인 스토어로 주기적으로 복사(materialize)해 최신 값을 유지합니다.

구분 오프라인 스토어 온라인 스토어
목적 모델 학습, 배치 추론 실시간 추론
데이터 양 과거 전체 이력 엔티티별 최신 값
응답 속도 초~분 단위 밀리초 단위

조회 방식 특정 시점 기준의 과거 값 엔티티 키로 최신 값
  • 시점 기준 조회(point-in-time)는 미래 정보 누수를 막는다
    • 3월 1일 거래의 사기 여부를 학습할 때는 3월 1일에 알 수 있었던 값만 써야 합니다.
    • 피처 스토어는 타임스탬프를 기준으로 그때의 피처 값을 가져옵니다. 2.3절 누수 표의 두 번째 줄을 막는 기능입니다.
  • 피처 스토어의 내부 구성은 세 가지다
    • 피처 서버는 REST나 gRPC로 피처를 제공합니다.
    • 피처 레지스트리는 사용 가능한 피처를 목록으로 관리합니다.
    • 피처 스토리지는 피처를 영속적으로 저장합니다.
  • 레지스트리는 실행마다 산출물 전부를 남긴다
    • 산출물은 모델, 플롯 이미지, 메타데이터, 하이퍼파라미터, 지표입니다.
    • 플롯 이미지는 손실 곡선과 혼동 행렬처럼 숫자 한 줄로 안 보이는 상태를 보여 줍니다.
    • 메타데이터는 데이터 버전, 코드 커밋, 실행 시각과 환경입니다. 모델 파일만으로는 "이 모델이 어디서 왔는가"에 답할 수 없습니다.
    • 레지스트리는 모델을 스테이징에서 운영으로 승격하고, /model/123 같은 엔드포인트로 노출할 수 있습니다. 승격과 롤백은 운영 표시를 옮기는 일이 됩니다.
  • 배포 자동화는 네 단계다
    • 트리거, 이미지 빌드, 컨테이너 레지스트리 푸시, 매니페스트 적용입니다.

4.3 MLOps에서 LLMOps로, 그리고 책의 세 프로젝트

LLMOps는 LLM 시스템의 운영입니다. 파이프라인, 배포, 모니터링은 LLM 시스템에도 그대로 씁니다.

MLOps 관심사 전통적 ML LLM 시스템에서 더해지는 것
데이터 준비 표·이미지 정제와 라벨링 문서 수집, 분할, 임베딩 생성
저장과 조회 피처 스토어 벡터 데이터베이스, 의미 기반 검색
평가 precision, recall, 오차 답변의 의미적 품질 평가
안전 입력 검증, 접근 통제 가드레일
비용 학습·서빙 자원 호출량과 토큰 비용
변경 관리 코드·데이터·모델 버전 프롬프트 버전

원리는 2.1절과 같습니다. 문서가 바뀌면 검색 결과가 바뀝니다. 프롬프트가 바뀌면 답이 바뀝니다.

장 그림 오른쪽의 컴포넌트 도구
12장 문서 수집 (PDF, MD, HTML) → 임베딩 → 벡터 DB → 검색 → 증강 → LLM 생성 text-embedding-004, FAISS·Pinecone·Chroma, Gemini·OpenAI·Claude
12장 트레이스 시각화, 프롬프트 관리, 토큰 추적, 비용 귀속 Langfuse
12장 스트리밍 응답과 출처 표시가 있는 채팅 UI Chainlit

13장 비용 모니터링, 프롬프트 최적화, 시맨틱 캐시, 모델 라우팅 (Flash Lite·Flash·Pro) RedisVL (시맨틱 캐시)

모델 라우팅은 질문의 난이도에 따라 단순 질문은 Flash Lite, 중간은 Flash, 복잡한 질문은 Pro로 보냅니다. 시맨틱 캐시는 의미가 같은 질문에 저장된 응답을 돌려줍니다. 둘 다 토큰 비용을 줄이는 장치입니다.

저자는 도구를 짧은 PoC로 시험해 사용 사례에 맞게 고르라고 권합니다.

책은 프로젝트 세 개를 씁니다.

MIDV-500은 여러 나라의 신분증·여권·운전면허증 견본을 스마트폰으로 찍은 영상 데이터셋입니다. 책상 위, 키보드 위, 손에 든 상태처럼 촬영 조건이 다양합니다. COCO의 91개 클래스에는 신분증이 없습니다. 그래서 라벨이 붙은 데이터로 YOLO를 미세 조정합니다.

MovieLens 1M은 2000년에 가입한 사용자의 익명 평점이고, users.dat, movies.dat, ratings.dat 세 파일입니다. 2.3절의 v1·v2·v3 조각 나누기를 이 데이터에 적용합니다.

표 데이터는 드리프트를 바로 잴 수 있습니다. 주행거리 열의 평균과 분위수를 계산하면 됩니다. 이미지는 밝기, 해상도, 임베딩 같은 대리 지표부터 설계해야 합니다. 그래서 책은 피처 스토어와 드리프트를 영화 추천 프로젝트로 설명합니다.
